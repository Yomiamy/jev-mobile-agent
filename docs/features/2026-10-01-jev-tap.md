# 功能規格：以 Jev 依描述點擊（mobile_tap）與精簡元素表

- **分支**：`feat/jev-decision`
- **狀態**：已實作並完成實機驗證（本文件為事後補記的 STAGE 0a 規格）
- **前置**：OCR 層（`mobile_list_elements_on_screen` 的 `ocr` 參數）已在 `main`

## 1. 問題

agent（MCP client，例如 Claude）每點一次，都要先 `mobile_list_elements_on_screen` 讀整份元素清單、自己挑目標、再抄 ref 或座標點擊：

- **耗 token**：FindRestaurant 首頁一次清單 7,681 字元，加上 OCR 更長；一個 11 步流程回傳給 agent 的工具結果約 5 萬字元。
- **清單大量浪費**：Flutter 把合併後的 label 重複印在每個子節點；畫面外的列（ListView 預先渲染、換頁後被推到背後的前一頁）也被列出。
- **座標由模型抄寫**：OCR 元素沒有 ref，只能由模型複製 `tap=x,y`，沒有任何防呆。

參考 [browser-use/jev-ultrafast](https://github.com/browser-use/jev-ultrafast)：由 TypeSafe 的 System One 模型 Jev 從「帶編號的元素表」中選出目標，一次請求、只能選實際觀察到的元素、低信心就不動作。

## 2. 目標與非目標

**目標**
1. 精簡元素表：只留畫面內、有內容的元素，重複的多行（合併）label 只印一次。
2. 新增 `mobile_tap({ device, target })`：agent 只給一句描述，由 Jev 選元素並點擊。
3. 沒把握就不點，回傳最接近的候選，讓 agent 退回 `list`。
4. 未設定 `TYPESAFE_API_KEY` 時行為完全不變。

**非目標**
- `mobile_run_goal`（由 Jev 同時決定操作與目標、server 端自跑迴圈）——另立專案。
- 解決 `dump ui` 本身的速度問題（見 §7，屬 mobilecli 範疇）。
- 辨識不在無障礙樹中的圖示（OCR 只讀文字）。

## 3. 方案比較

| 方案 | 內容 | 取捨 | 結論 |
|---|---|---|---|
| A. 依描述點擊 | 新增 `mobile_tap`，每次點擊由 Jev 從元素表選目標 | 改動小；agent 仍掌控流程；每次點擊多一次 Jev 請求 | ✅ 採用 |
| B. 目標驅動迴圈 | `mobile_run_goal(goal)`，Jev 每步選操作＋目標 | 最快（jev-ultrafast 的主因）；工作量大，DONE 需獨立驗證 | 延後 |
| C. 只精簡清單 | 不導入 Jev，只縮短 `list` 輸出 | 零外部相依；仍由 agent 讀清單、抄座標 | 併入 A 作為前置 |

## 4. 設計

### 4.1 資料流

```
mobile_tap(target)
  ├─ getScreenSize()
  └─ 最多 2 次嘗試：
       dump 無障礙樹 → compactElements() → chooseElement(Jev)
         └─ 無把握且為 macOS → withOcrElements() → compactElements() → chooseElement(Jev)
       無把握 → 不點擊，拋 ActionableError（附前 3 名候選與機率）
       有 ref 且 robot 支援 → tapByRef(ref)；否則 → tap(元素中心)
       tapByRef 回報「not found on current screen」→ 重新 dump 再選一次
```

### 4.2 元件

| 檔案 | 職責 |
|---|---|
| `src/compact-elements.ts` | `compactElements(elements, screen)`：去掉畫面外元素（螢幕尺寸未知時略過此步）、沒有內容的容器（純圖示按鈕類型保留）、重複 label 只留第一次 |
| `src/jev.ts` | `buildRequest` 組 Choice 問題（每元素一個選項＋`NONE`，元素描述含類型、文字、中心點、尺寸）；`parseAnswer` 驗證並映射回元素；`isConfident`；`chooseElement` 呼叫 `POST https://api.typesafe.ai/v1/systemone` |
| `src/server.ts` | `list` 輸出套用 `compactElements`；`isJevEnabled()` 時註冊 `mobile_tap` |

### 4.3 決策規則

- **信心門檻**：`MIN_CONFIDENCE = 0.5`，手動訂定，程式內以 `ponytail:` 註解標示待以實測資料調整。
- **選項上限**：Jev Choice 最多 255 個選項，元素數 ≥ 255 時拒絕並請 agent 改用 `list`（精簡後首頁約 50 個）。
- **Jev 只能選觀察到的元素**：回答指向不存在的選項 → 視為無效回答，不點擊。

### 4.4 錯誤處理

| 情況 | 行為 |
|---|---|
| TypeSafe 回 HTTP 錯誤、逾時（15 秒）、網路錯誤、回應不是 JSON | `ActionableError`，不點擊 |
| 回答格式無效（含 `null` 回應、`probabilities` 為 `null`、confidence 非有限數、選項不是送出的 key） | `ActionableError`，不點擊；`probabilities` 中非數字的值不列入候選 |
| NONE 或信心 < 0.5 | `ActionableError`，附候選 |
| ref 失效 | 重新 dump、重選，最多 2 次嘗試 |

### 4.5 隱私

`mobile_tap` 會把畫面元素文字（含 OCR 文字）送到 TypeSafe。畫面可能含帳號 email 等個資，README 已註明，僅在有 key 時啟用。

## 5. 驗收標準

1. 無 key：工具清單與原本一致，所有既有測試通過。
2. 有 key：註冊 `mobile_tap`，annotation 為 `{ readOnlyHint: false, destructiveHint: false, openWorldHint: true }`。
3. 目標存在時點中；目標不存在時不點擊。
4. 樹中找不到的文字可經 OCR 找到並點中。
5. 畫面在讀取與點擊之間改變時，不點到過期目標。

## 6. 驗證結果

### 6.1 單元測試

有 key、無 key 兩種環境皆 **50 passed**；`npm run lint` 無問題。新增 `test/compact-elements.test.ts`（6 案例，含橫向畫面）、`test/jev.test.ts`（14 案例：stub `fetch` 的逾時、網路錯誤、HTTP 503、`null` 回應、非 JSON 回應，以及以假 robot 驗證 `tapByDescription` 的 ref 點擊、座標點擊、無把握不點、ref 過期重讀）。

STAGE 3 審查後的調整：畫面內判斷改以螢幕長邊為界（部分 robot 回報直向尺寸而元素座標為目前方向，原寫法會在橫向時刪掉畫面右半的元素）；點擊流程由 `src/server.ts` 移到 `src/jev.ts` 的 `tapByDescription`，`server.ts` 只保留註冊。

| 處理 | 元素數 | 字元數 |

| 原始 | 70 | 7,681 |
| 只留畫面內 | 56 | 6,092 |

| | 不用 Jev | 用 Jev |
|---|---:|---:|
| 總耗時 | 77 秒 | 89 秒 |

## 7. `dump ui` 慢的根因調查

每次 `mobile_tap` 的耗時（4–44 秒）幾乎都花在 mobilecli 的 `dump ui`，Jev 每次請求約 0.3 秒。

**根因**：mobilecli 1.0.16（目前最新版）偵測到前景 app 為可除錯（debuggable）的 Flutter app 時，不走 Android 無障礙 dump，改經 Dart VM service 走訪整棵 render tree（`docs/using-flutter.md`、`devices/android_flutter.go`）。每個 render object 需 10–25 次 VM service `invoke`（widget key、`debugSemantics` 各欄位、`getSemanticsData`、子節點、座標），且走訪範圍包含畫面外的列與背後的前一頁；耗時與 render object 數量成正比。沒有環境變數或參數可關閉此路徑。

| 情況 | `dump ui` 耗時 |
|---|---:|
| mobilecli，原生畫面（launcher，agent 已啟動） | 0.70 秒 |
| mobilecli，Flutter debug app（VM service 路徑） | 6.3–10.2 秒 |
| mobilecli，agent 剛重啟後第一次 | 12.8 秒 |
| `uiautomator dump` 指令（每次新開 process，launcher 或 Flutter 畫面皆是） | 3.1–8.4 秒 |

調查過程中的更正：初次量到的「`uiautomator dump` 0.45 秒」無效——mobilecli agent 佔用 UiAutomation，該指令被 kill（rc=137）；「廣告 WebView 動畫導致等待 idle」的假設亦不成立。

**未驗證**：同一 app 改用非 debug build（`flutter build apk --profile`）時，mobilecli 會改走無障礙 dump，推測可大幅加速；且實測無障礙 dump 會帶出按鈕 tooltip（如右上角 `Button "AI 覓食助理"`），VM service 路徑反而沒有。

## 8. 已知限制與後續

| 項目 | 說明 |
|---|---|
| 相同目標重複出現 | 兩個等價目標會分散機率而被拒絕，agent 需寫出更具體的描述（位置等） |
| 無 label 的按鈕信心偏低 | 選單按鈕僅 0.60–0.66；app 端補 `tooltip`／`Semantics(label:)` 可根本改善 |
| 門檻未校準 | 0.5 為手訂，需累積實測紀錄後調整 |
| Jev token 未記錄 | 應記錄 TypeSafe 回傳的 `usage`，才能比較總成本 |
| 確認畫面仍用 `list` | 11 步流程中 2 次 `list` 約佔 8 成字元；可改用「等待文字出現」類工具 |
| 速度 | 受 `dump ui` 限制；先驗證 profile build，再考慮向 mobilecli 回報（只走訪畫面內子樹、合併 `invoke`） |
| TypeSafe 失敗無重試 | 逾時、網路錯誤、HTTP 錯誤、非 JSON 回應一律轉為 `ActionableError` 交回 agent，不重試 |
| 座標點擊沒有過期防護 | 只有 ref 路徑會由 mobilecli 拒絕過期目標；OCR 元素與 legacy robot 以座標點擊，畫面在讀取與點擊之間改變時會點到舊位置。ref 是否真能偵測過期取決於 mobilecli 的 ref 語意（實測 `@e65` 在多次 dump 間不變，疑似依走訪順序編號），尚未確認 |
| 做法 B | `mobile_run_goal` 尚未開始 |
